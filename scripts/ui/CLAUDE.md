# scripts/ui

Owns: main menu, host/join lobby screen, in-game HUD (health, ammo, weapon), pause menu.

Depends on: `scripts/networking` (host/join actions), `scripts/player` (HUD data).

## Status

- `main_menu.gd` (`class_name MainMenu`, `scenes/levels/main_menu.tscn`) — `project.godot`'s `run/main_scene`, and where both of `hud.gd`'s game-over buttons return to. One `Start` button, which begins a fresh solo run (`change_scene_to_file` to `scenes/levels/town.tscn`) - no host/join flow yet, since `scripts/networking` isn't built. Resets `Input.mouse_mode` to visible in `_ready()`, since a run that just ended left it captured for gameplay. Shows a "last run" line (round/points/kills) when `GameState.has_last_run` is true - see `scripts/networking/game_state.gd`.
- `hud.gd` (`class_name HUD`, `scenes/ui/hud.tscn`) — the in-game HUD, instanced into `player.tscn` as `HUD`. Health bar and value bottom-left, weapon name and `mag / reserve` ammo bottom-right, and a weapon-name toast above centre that fades after a switch.

  **`GameOverOverlay`** is the only listener anywhere on `Player.died` - before this was added, the signal fired into nothing and a dead player just sat there, frozen, forever. `_on_died()` looks the round director up fresh by group (matching `_bind_round_director()`'s own approach) to build the "Round N · points · kills" stats line, writes them into `GameState.record_run_end()` so `main_menu.gd` can show them, and releases `Input.mouse_mode` back to visible so its two buttons (`Retry` - `reload_current_scene()`; `Main Menu` - back to `main_menu.tscn`) are actually clickable.

  **It is a pure view.** It holds no game state and never reads from the player or the weapon; `bind_player()` connects it to `health_changed`, `ammo_changed`, `weapon_changed`, `aim_changed` and `fired`, and everything after that arrives by signal. That keeps gameplay ignorant of what's on screen, and means a second local player or a spectator can bind its own instance to a different source.

  `bind_player()` also catches up on the current weapon and ammo by hand. The starting weapon is equipped in `WeaponController._ready()`, which runs *before* the player binds the HUD — children are readied before their parent — so that first `weapon_changed` would otherwise be missed and the readouts would sit on the scene's placeholder text until the first switch.

  Ammo colours amber below 30% of a magazine and red when empty; the health bar lerps green to red. Both are so state reads at a glance without parsing digits.

  **Round readout and points**, added with the game loop. `RoundPanel` (top centre) shows `ROUND 07` plus a status line that reads `12 remaining` while there's work left and switches to `clear · next in 6s` once the round is done — the countdown is only surfaced when it's the thing the player is actually waiting on. `PointsPanel` (bottom left, above health) shows the balance, digit-grouped because points reach five figures by the mid rounds and unseparated digits stop being readable at a glance.

  These come from the level's `RoundDirector` rather than from the player, found by group in `_bind_round_director()`. That lookup is **deferred a frame on purpose**: the director is a sibling up in the level while the HUD is nested inside the player scene, so which is ready first depends on the order they happen to sit in the level tree — a detail nobody should have to preserve when rearranging a scene. A level with no director is legitimate (weapon test scenes have none) and simply hides the round readout.

  **Colours are the browser build's palette**, carried over so the two versions look like the same game: amber `#e8a33d` for points, bone `#e6e0d2` for secondary text, blood `#a3231e` for the round number.

  **`InteractPrompt`** (centre screen, below the crosshair) shows/hides off `Player.interactable_changed(prompt_text)` - an empty string hides it. The text itself (cost, owned/afford/maxed state) is built entirely by whichever `scripts/economy/*.gd` `Interactable` is currently nearest; the HUD just prefixes it with "Press E - ".

  **`DownedOverlay`** (full-screen red tint + `Countdown` label) shows on `Player.downed(duration)`, hides on `Player.revived`. The countdown itself ticks down locally in `_process()` rather than re-reading state from the player every frame - `duration` is all the info needed at the moment it goes down.

- **`PerkStrip`** (`HUD/PerkStrip`, bottom-left, above `PointsPanel`) grows a green chip for each perk as `Player.perk_granted(key)` fires - `JUGGERNOG`, `SPEED COLA`, etc. Only ever adds, never removes or rebuilds: perks are one-time and permanent for the run (`Player.grant_perk()` refuses a repeat), unlike the loadout strip below, which does have to rebuild since a weapon slot's contents actually change. Display names come from a fixed `PERK_DISPLAY` table in `hud.gd`, not from whichever `PerkMachine` granted the perk - `grant_perk()` only ever carries the key, and the six keys are a closed set (see `scripts/economy/CLAUDE.md`), not something a machine could introduce a new one of at runtime.
- **The points-multiplier readout is `PointsPanel/PointsCaption`'s text**, not a new node - `_on_round_started()` sets it to `POINTS  ·  x1.00`-style text via `RoundDirector.round_multiplier(round_number)`, the exact same static function `points_for_hit()` already uses to compute every award. Reusing it rather than a parallel formula means the readout can't drift from what a kill is actually worth.
- **`LoadoutStrip`** (`HUD/LoadoutStrip`, bottom-right, above `AmmoPanel`) lists every carried weapon - `1 MAKAROV  2 AK-47` - dim for a carried weapon that isn't currently in hand, bright for the one that is. Rebuilt from scratch in `_refresh_loadout_strip()` on every `weapon_changed` rather than diffed: `grant_weapon()` always equips whatever it just granted (see `scripts/weapons/CLAUDE.md`), so a switch is the only moment the loadout can have changed too, and this is a handful of `Label`s, not a per-frame cost. Reads `weapon_controller.loadout` directly rather than through a signal - the one place in this file that does, alongside the existing weapon/ammo catch-up in `bind_player()` - since there's no dedicated "loadout changed" signal and adding one for a single reader seemed like more machinery than the HUD's signal-only rule is actually protecting against here. Only carried (non-`null`) slots show; an empty entry for every uncarried slot up to `weapon_cap` read as clutter rather than useful "room for one more" information.
- `crosshair.gd` (`class_name Crosshair`, `HUD/Crosshair`) draws a resolution-independent centred crosshair. It tightens in ADS, expands with normalized movement speed (fed per-frame by the player, since that's not signal data), and pulses on `fired`. **Hidden outright while aiming in first person** (`is_aiming and is_first_person`, both driven by signals - `Player.perspective_changed` alongside the pre-existing `aim_changed`) - first-person ADS lines the camera up with the weapon's own sight (`WeaponController._update_ads_sight_alignment()`), so a screen-centre dot drawn on top of it would be redundant at best and visibly off from the actual sight picture at worst. Third-person ADS keeps the reticle, since there's nothing else to aim by from over the shoulder.

- `hitmarker.gd` (`class_name Hitmarker`, `HUD/Hitmarker`) flashes a four-tick X on `WeaponController.hit_confirmed`, white for a hit and blood-red for a kill. Hitscan gives no other feedback — the shot is instant and the target is usually behind other targets — so without it the player can't tell a hit from a miss. Ticks sit at 45° so they frame the crosshair rather than overlap it, and it fades rather than blinking off so automatic fire reads as a sustained marker instead of a strobe.

- **`PauseOverlay`** (`HUD/PauseOverlay`) shows on `Player.paused_changed(true)`, hides on `false`. `player.gd` owns the actual pause: `ui_cancel` (Esc) toggles `get_tree().paused` directly in `_set_paused()` - which is also what freezes zombies, the round timer, and everything else, since none of them override `process_mode` - releases/recaptures the mouse to match, and emits the signal this listens for. Blocked while `is_dead`, so Esc after a death doesn't fight the game-over overlay for the screen. `ResumeButton` calls back into `player.resume()` rather than unpausing directly, since `_set_paused()` also owns the mouse-mode/signal side of the transition; `PauseMainMenuButton` unpauses first and then changes scene, same as `GameOverOverlay`'s button - handing `main_menu.tscn` a scene that's already paused would freeze it on arrival.
  **`PauseOverlay` alone is `process_mode = PROCESS_MODE_ALWAYS`** (`3`, set in `hud.tscn`) - the rest of the HUD stays default and freezes with everything else. Without this its own buttons would never receive a click while the tree is the thing that's paused.
  **Every existing `get_tree().create_timer()` call needed `process_always=false` added** (`round_director.gd`'s round-start delay, `player.gd`'s downed/revive timers, `zombie.gd`'s corpse cleanup, `weapon_controller.gd`'s VFX expiry) - `SceneTreeTimer` defaults `process_always` to `true`, meaning every one of them would otherwise keep counting through a pause: a round could autostart, a downed player could auto-revive, or a corpse could vanish while sitting in the pause menu. A `_process(delta)` accumulator (like `RoundDirector`'s own between-round countdown) doesn't have this problem - it already stops with the node's default `process_mode` - so it's specifically `create_timer` that needs the explicit flag.

## Known gaps

- Damage-direction indicators are not implemented. `main_menu.tscn` exists now but is solo-only (a single `Start` button) - no host/join lobby screen, since `scripts/networking` isn't built yet.
- **No reload indicator.** `reload_started(duration)` is emitted and unused by the HUD — a progress arc round the crosshair is the obvious use for it.
