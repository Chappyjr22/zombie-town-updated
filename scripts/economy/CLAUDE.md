# scripts/economy

Owns: spending points on things - wall buys, ammo buys, perk machines, Pack-a-Punch, and the buyable doors that gate building access. Ported from zombie-town-online's `addWallBuy`/`addAmmoBuy`/`addPerkMachine`/`addPackAPunch` (all procedural geometry there too, not downloaded assets - see `tools/build_town_level.gd`, which is what actually places instances of everything below).

Depends on: `scripts/player` (`Player.points`/`spend_points()`/`perks`/`register_interactable()`), `scripts/weapons` (`WeaponController.loadout`/`grant_weapon()`/`refill_weapon()`/`pack_upgrade()`).

## Status

- `interactable.gd` (`class_name Interactable`, extends `Area3D`) is the base every machine/door subclasses. Its own `CollisionShape3D` (added by whoever places it) is the range a player has to be inside; `body_entered`/`body_exited` register/unregister it with the player (`Player.register_interactable()`), rather than the player scanning the world for nearby machines every frame. `attempt_purchase()` is the shared afford-check/spend/apply flow - subclasses override `prompt_text()`, `_can_interact()`, and `_apply()`, not `attempt_purchase()` itself, **unless the cost is dynamic** (`wall_buy_station.gd`'s owned/not-owned price, `pack_a_punch_machine.gd`'s per-tier price), in which case the subclass overrides `attempt_purchase()` directly instead of relying on the base class's fixed `cost` export.
- `wall_buy_station.gd` grants a `WeaponData` the player doesn't have yet, or refills its ammo at half price if they already do (`own ? cost/2 : cost`, same as the JS source). The player starts with one weapon (`player.tscn`'s `loadout` is `[pistol, null, null, ...]`) - everything else only exists via one of these.
- `ammo_buy_station.gd` - flat-price refill, refuses if the weapon isn't owned yet.
- `perk_machine.gd` grants a named perk once (`Player.perks[key] = true`, refuses a repeat buy). Six keys, costs/effects match the JS source's `PERKS` table: `jugg` (Juggernog, 2500, `max_health` 100→250 + full heal - applied inside `Player.grant_perk()`, not here, since health has nowhere else to live), `speed` (Speed Cola, 3000, `WeaponController.reload_speed_multiplier = 0.5`), `dtap` (Double Tap, 2000, `WeaponController.dtap_multiplier = 1.5` - the original alternates between "fires faster" and "hits harder" across games, damage was picked here since it reuses the same multiplier plumbing as Pack-a-Punch), `stamin` (Stamin-Up, 2000, `Player.speed_multiplier = 1.25`), `mule` (Mule Kick, 4000, `WeaponController.weapon_cap` 2→3), `revive` (Quick Revive, 1500, enables the downed/self-revive state machine in `scripts/player/player.gd` - see that file's `CLAUDE.md`).
- `pack_a_punch_machine.gd` upgrades the currently-held weapon, two tiers (`WeaponController.PACK_DAMAGE_MULTIPLIER`/`PACK_CAPACITY_MULTIPLIER`/`PACK_COST` - `[1, 2.0, 3.4]` damage, `[1, 1, 1.5]` mag/reserve, `[5000, 15000]` cost, ported directly from the JS source's own numbers). Tier is tracked per loadout slot (`WeaponController._pack_level`), **never** by mutating a `WeaponData` resource - `load()` caches and shares one instance across every reference to a given `.tres`, so writing to it would upgrade that weapon for every slot/player holding it, not just the one that got packed.
- `buyable_door.gd` blocks a building's one entrance (see the level-generation note below) until bought, then `queue_free()`s both itself and its `door_body` (a plain `StaticBody3D` sibling, wired up by the generator - an `Area3D` never blocks movement no matter what collision layer it's on, so the solid door has to be a separate node).
- `mystery_box.gd` (`class_name MysteryBox`) grants a random `WeaponData` from its `wonder_weapons` export - the five box-exclusive wonder weapons, never wall-buyable (`scripts/weapons/CLAUDE.md` has the full list and source data). Rerollable any number of times, cost defaults to 950 if unset ("nine hundred and fifty a roll" per the source's own flavor text) - `_apply()` prefers a weapon the player doesn't already own, falling back to the full pool once every entry is owned. Drops to 10 during Fire Sale (below) - overrides `attempt_purchase()` rather than relying on the base class's fixed `cost`, same reason `wall_buy_station.gd` does. Placed once, opposite the fountain from Pack-a-Punch - not verified against the level visually.
- `power_up_drop.gd` (`class_name PowerUpDrop`, extends `Area3D`) - **not** an `Interactable` subclass, since power-ups are walked into rather than pressed E on (matches the source's own contact pickup). Ported from `zombie-town-online`'s `DROPS`/`buffs`/`maybeDrop()`/`applyCollectedDrop()`:
  - **Spawning**: `RoundDirector._maybe_drop_power_up()`, called from `_on_zombie_died()` after `kills` increments. `POWER_UP_DROP_CHANCE` (2.8%) per kill, or guaranteed every `POWER_UP_GUARANTEED_EVERY` (60) kills regardless of the roll - ported numbers, not tuned here. Placed with `position` set before `add_child()`, same rule as `_spawn_one()` above.
  - **Five kinds**, uniform random: `maxammo` (`WeaponController.refill_all_ammo()` - every carried weapon, not just the one in hand), `instakill` (sets `Player.instakill_remaining`), `doublepoints` (sets `Player.doublepoints_remaining`), `firesale` (sets `Player.firesale_remaining`), `nuke` (instant - kills every zombie currently alive via `take_damage(999999.0)`, then `Player.award_points(400)`, which is itself still subject to Double Points if that happens to also be active - matches the source calling its own already-multiplier-aware `addPoints()` for the nuke reward too).
  - **Timed buffs are 30 seconds** (`Player.POWER_UP_DURATION`), ticked down in `Player._process()` rather than owning a `Timer` each - same pattern as everything else timed on the player. `instakill`/`doublepoints` are read where they take effect (`WeaponController._effective_damage()`, `Player.award_points()`), not applied at pickup time, so nothing needs undoing if the timer runs out mid-effect.
  - **Visuals are a plain glowing sphere + a text label**, not a port of the source's own sculpted per-kind models (a skull for Insta-Kill, an ammo crate for Max Ammo, etc.) - same reasoning as the wonder-weapon placeholder models: no way to verify hand-built geometry looks right without ever being able to see it.

## Level integration

`tools/build_town_level.gd` reduced every building to **one entrance** and added a blocking pane to every gap that used to be a second, free door (a `wall_run` gap with no `sill` is a floor-to-head opening - nothing about it was ever actually solid before this, regardless of whether the JS called it a "window" or a "door"). A paid door only means something if there's no free way around it.

## Known gaps

- **No power sub-mechanic.** The JS source gated some perk machines behind a separate "turn on power" step (`requiresPower`); this pass skips it entirely (confirmed with the user) - every perk machine works as soon as its building is paid into.
