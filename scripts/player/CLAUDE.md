# scripts/player

Owns: third-person movement (jog/sprint/crouch/jump), the orbiting camera rig, local player input handling, health/damage state for the local player.

Depends on: `scripts/weapons` (equips/fires weapons — wired up), `scripts/common` (`NodeUtils`, for reaching into the imported model), `scripts/networking` (broadcasts local state to peers — not yet wired up).

## Status

`player.gd` (`scenes/player/player.tscn`) implements:

- Movement: WASD jog, Shift sprint (forward-only), Ctrl crouch (smoothly resizes the capsule and lowers the camera rig), Space jump. Mouse is captured on `_ready()`; `ui_cancel` (Esc) toggles capture.
- Aiming: hold right mouse (`aim`). `WeaponController` narrows the camera FOV and reduces mouse sensitivity while the player pulls the camera in over the shoulder; releasing returns smoothly. Reloading cancels aim.
- `HUD/Crosshair` stays centered, tightens while aiming, expands with movement, and pulses outward on each shot.
- `mixamo_soldier.glb` attached as the visible body (`Model` node) — a consolidated Mixamo Gasmask Soldier model with gameplay clips baked into one runtime asset; see `ASSET_MANIFEST.md` for clip names.
- `scripts/weapons/weapon_controller.gd` wired up under `CameraRig/SpringArm3D/Camera3D` — see `scripts/weapons/CLAUDE.md`.
- `health` / `take_damage(amount)` / `died` signal, and joins the `"player"` group so `scripts/ai/zombie.gd` can find and target it. `class_name Player`.
- **Health regenerates** after `REGEN_DELAY` (5.5s) clear of damage, at 10% of max per second — ported from the browser build. The delay is the whole mechanic: it rewards breaking contact, which is what makes kiting a round the right way to play it rather than trading hits.
- **`points`, and `award_points()`** with a `points_changed(total, delta)` signal. The player converts `WeaponController.hit_confirmed` into points via `RoundDirector.points_for_hit()`, looking the director up by group — so the weapon knows nothing about scoring and the director knows nothing about who is shooting. `spend_points(amount)` is the other direction — every `scripts/economy/*.gd` purchase goes through it; it refuses rather than going negative. Starts at 500, once, at game start — not a per-round refill, since `RoundDirector` never resets player state between rounds.
- **`perks: Dictionary`**, granted by `scripts/economy/perk_machine.gd`'s `grant_perk()`. Persists for the whole session — nothing resets it between rounds. Most perks are read at the point of use by whoever owns the relevant stat (`WeaponController.reload_speed_multiplier`/`dtap_multiplier`/`weapon_cap`, `speed_multiplier` here); Juggernog (`max_health`) and Quick Revive (below) are the two exceptions, applied directly since they have nowhere else to live.
- **Power-up buffs** (`instakill_remaining`/`doublepoints_remaining`/`firesale_remaining`, all in seconds, `POWER_UP_DURATION` = 30) - unlike perks, these are timed and granted by `scripts/economy/power_up_drop.gd`'s contact pickup rather than a purchase. Ticked down every frame in `_process()`, not owned by a `Timer` node each. Read where they take effect rather than applied at pickup time: `has_instakill()` by `WeaponController._effective_damage()`, `doublepoints_remaining` inline in `award_points()`, `firesale_remaining` by `MysteryBox._current_cost()`. Nothing needs undoing when one expires - the read site just stops seeing it as active.
- **Downed/self-revive state** (`is_downed`, `is_invincible`). Only reachable with Quick Revive owned — `take_damage()` still just kills outright without it, since solo play has no one to revive you. Going down locks input out (`_is_incapacitated()`, extending the existing `is_dead` gates throughout this file) for `DOWNED_DURATION` (5s), then auto-revives to `REVIVE_HEALTH_FRACTION` of max health with `REVIVE_INVINCIBILITY_DURATION` (4s) of `take_damage()` immunity — chosen over making zombies path away during the window, since it needed no changes to `scripts/ai/zombie.gd`. No dedicated downed/crawl animation exists on `mixamo_soldier.glb`; `crouch_idle` stands in, held on its last frame.
- **Interaction** (`register_interactable()`/`unregister_interactable()`, called by `scripts/economy/interactable.gd`'s own `Area3D` signals rather than this file scanning the world). `_update_interaction()` picks the nearest of whatever's currently in range, emits `interactable_changed(prompt_text)` for the HUD, and fires it on an "interact" (E) press.
- **Pause** (`ui_cancel`/Esc, in `_unhandled_input()`) toggles `get_tree().paused` via `_set_paused()`, which is also what freezes zombies/the round timer/everything else - no per-system pause logic needed, since nothing overrides its default `process_mode`. Releases/recaptures the mouse to match and emits `paused_changed(bool)`, which `HUD/PauseOverlay` listens for - see `scripts/ui/CLAUDE.md` for the overlay side and the `SceneTreeTimer` `process_always` fix this needed elsewhere. Refused while `is_dead`, so it can't fight the game-over overlay for the screen.
- **Third-person camera.** `CameraRig → SpringArm3D → Camera3D`. The rig is offset on X to keep the character out of the middle of the screen, and rides the capsule's height so crouching lowers the view (`_update_crouch()` rewrites `camera_rig.position.y` every physics tick, unconditionally). The spring arm collides with `WORLD` only — including actors would slam the camera forward every time a zombie walked behind the player. Aiming shortens the arm (`camera_aim_distance`) **and** shrinks the shoulder offset itself (`camera_aim_shoulder_offset`, `_update_camera_distance()` rewrites `camera_rig.position.x`) on the same lerp - the first half of ADS sight alignment, the coarse half; `scripts/weapons/weapon_controller.gd`'s `_update_ads_sight_alignment()` does the fine remainder on `SpringArm3D`. See that file's CLAUDE.md for why the two are split across two nodes rather than one doing the whole correction: `CameraRig.position` already has two owners here (`.y` from crouch, `.x` from this), and nothing else may write to it without either coordinating with both or picking a different node in the chain.
- **First person is a toggle (`toggle_perspective`, `V`), not a separate mode with its own assets.** `is_first_person` retargets the same third-person camera rig rather than swapping in a viewmodel - see `docs/ARCHITECTURE.md`'s "Why not first person" for why a viewmodel isn't on the table here. `_update_camera_distance()` still collapses `spring_arm.spring_length` to 0 for both perspectives (no boom - the camera sits at `CameraRig`'s own origin), but `CameraRig.position` itself is fully repositioned every frame by `_update_first_person_camera()` while first person is active, off the **live `mixamorig_Head` bone** rather than a fixed offset - the first version used a fixed capsule-relative offset (mirroring `_update_crouch`'s third-person one), which only agreed with where the head actually was at a rest pose; the rifle sprint clip in particular swings the whole upper body well off that, and a camera that hadn't moved with it read as clipping *out* through the character's own face and chest during movement rather than staying enveloped. Tracking the bone directly (no lerp - see that function's own comment on why a second smoothing pass would lag behind fast motion instead of fixing it) keeps the camera coincident with the head mesh through whatever clip is playing.
  Three knobs nudge off that live bone position: `fps_eye_height_offset` (up, since the bone sits at the neck/skull joint, not the eyes), `fps_forward_offset` (forward, past the face), `fps_x_offset` (left/right, default 0) - eye-tuned to `0.15`/`0.16`/`0.07`. **The forward offset exists because `mixamo_soldier.glb` is one skinned mesh with no separable head surface** - checked before assuming a split-mesh/shader-based head-hide was available - so a camera placed exactly at the bone sees the inside of its own skull; pushing it forward past the face is the cheap workaround, and looking straight down at the chest/collar can still clip. Nothing about the weapon/hand rig changes between modes - same world model, same `_solve_support_arm_ik()`, same `_update_ads_sight_alignment()`.
  **`_update_crouch()` skips its own `camera_rig.position.y` write outright in first person, not just leaves it to be overwritten.** It used to just let `_update_first_person_camera()`'s "runs later in `_process()`" ordering win, on the assumption that later-in-the-frame wins - but `_update_crouch()` runs on the *physics* tick and `_update_first_person_camera()` on the *idle* one, two different clocks, so "runs later in the same frame" doesn't hold the way it would if both were on the same one. Left running, it directly raced the idle-tick function for the same property, snapping `camera_rig.position.y` back to the third-person chest-height formula on whichever physics tick happened to land between two idle frames - caught because `_update_ads_sight_alignment()`'s residual was growing *erratically* instead of converging, not because anyone could see the snap itself.
  **`MAX_AIM_YAW` and `spine_pitch_share` are both third-person-only ceilings**, replaced by `MAX_AIM_YAW_FIRST_PERSON` (90°, vs. 40°) and `spine_pitch_share_first_person` (1.0, full match, vs. 0.75) while `is_first_person` is true. Both existed to stop `_apply_spine_aim()`'s torso correction from visibly over-twisting *as seen from third person* - a concern that doesn't apply once the player is looking out through the head instead of watching it from outside. Found while wiring up first-person ADS: `aim_yaw` was pinning at the old 40° ceiling and staying there, because first person's camera position needs a bigger torso correction than third person's ever did to bring the barrel in line - a permanent, visible sight/crosshair mismatch for as long as ADS was held, not a slow convergence.
  **Even with both ceilings freed, a probe found a real, un-explained residual - roughly 0.12m of the crosshair-to-sight gap `_update_ads_sight_alignment()` can't close, stable rather than still converging (traced well past where the correction settles).** The race fix took it from erratic and unbounded to consistent; freeing the two ceilings took it from ~0.6m+ down to ~0.12m; neither fully closed it. Current best guess: `sight_in_mesh` is a heuristic point (`grip.position + along_barrel * 0.5 + Vector3.UP * 0.04 + sight_nudge` for a socket-fit weapon - see `scripts/weapons/CLAUDE.md`), not a hand-placed marker, and spine-aim only ever corrects the barrel's *direction* while ADS corrects the camera's *position* - two related but not fully equivalent objectives, close enough that third person's forgiving margin never exposed the gap between them. Not chased further this session; `WeaponData.sight_nudge` (per-weapon) is the intended knob for exactly this kind of residual and is worth trying before any more architecture work here - it just couldn't be usefully tuned until the residual stopped moving around underneath it.
- **Mouse yaw turns the body, not the camera.** Pitch goes on the spring arm. The character therefore always faces where the camera looks, which is what makes the directional walk/strafe blend space meaningful and keeps shots landing on the crosshair.
- `_apply_spine_aim()` turns the torso so the held weapon points where the camera does — pitch straight from the camera angle, yaw from the error actually left between the barrel and the view (`_measure_aim_yaw_error()`). Converges to zero at idle and while jogging; deliberately released during a sprint, where the empty-handed clip would demand ~70° of twist. Runs in `_process` because the `AnimationTree` rewrites bone poses every frame — see the `process_priority` note in `_ready()`.
- **No hit reaction.** `take_damage()` deliberately plays nothing. The clip is a full-body flinch that interrupts aiming and sprinting, and losing control every time a zombie connects felt worse than showing nothing. Damage feedback belongs on the HUD.
- **Locomotion clips come from packs, not from the model.** `_install_extra_clips()` loads every set in `INSTALLED_SETS` as loose `Animation` resources, installed under set-namespaced names (`rifle_run_forward`, `pistol_strafe`) so both live in the library at once. The model's own locomotion is largely empty-handed and is not used. Regenerate with `tools/build_clips.gd -- <set>`; check the tables with `tools/verify_locomotion_sets.gd` and the clips themselves with `tools/probe_locomotion_sets.gd`.
- **The stance follows the weapon.** `locomotion_sets.gd` maps a set name to a clip per tier and direction; `WeaponData.locomotion_set` picks one, and `_on_weapon_changed()` re-points every blend point at the new set. The tree is never rebuilt — a switch is a keypress and shouldn't touch the disk. An unknown set name falls back to `rifle`, and a set missing any clip is refused wholesale rather than applied partially, since a square with dead points is a character who freezes when they strafe.
  Names are built from the tables rather than scanned off disk: exported builds turn loose `.res` into `.remap`, so a directory scan works in the editor and quietly finds nothing in a shipped game.
- **Locomotion is three tiers**: `normal` (a jog — this is the default gait) → `sprint` → `crouch`, each a nine-point blend square. A set with no sprint clips of its own (the pistol pack has none) stays on the normal tier and speeds its stride up by `SPRINT_SPEED / WALK_SPEED` through the `LocomotionSpeed` time scale instead — crossfading a tier into a copy of itself blends a clip against a phase-shifted version of itself and mushes the legs together.
- **Animation driven by movement and weapon state.** A runtime `AnimationTree` uses 2D blend spaces for forward, backward, left, right, and interpolated diagonal movement, blending jog to sprint and standing to crouching. Weapon fire/reload signals drive spine-and-arms-only one-shots over locomotion, while jump, landing, hit, and death remain prioritized full-body animations.
- **`model_yaw_offset_degrees` (default 180)** rotates the `Model` node's local Y to correct Mixamo's authored-front-axis mismatch with Godot's forward direction.

## Known gaps

- **First person's camera placement has been eye-tuned once already** (`fps_eye_height_offset`/`fps_forward_offset`/`fps_x_offset`) but is still worth another look after any locomotion/animation change - the head-bone tracking means the sprint clip's own swing is fully visible through the camera now, which can read as more head-bob than wanted; if so, the fix is damping the *tracked position itself* in `_update_first_person_camera()`, not reintroducing a lerp on top of it, which would just reintroduce the lag it was written to avoid. Also expect the support-hand grip/weapon fit to need another look after any weapon change, since a rifle-length gun and an approximate hand-wrap read very differently at eye distance than they did over-the-shoulder.
- ~~First-person ADS's crosshair-to-sight residual is unresolved~~ **Resolved, by replacing the correction rather than improving it.** The bone-driven weapon position this was chasing turned out to be the actual problem - `MAX_AIM_YAW_FIRST_PERSON`/`spine_pitch_share_first_person` above got the *torso* pointing the weapon at the camera as well as a rotation-only correction on a live-animated skeleton ever could, but "as well as it could" still wasn't exact or stable, because the target it was chasing never stood still. `scripts/weapons/CLAUDE.md`'s `_apply_first_person_weapon_hold()` entry sidesteps this instead of continuing to chase it: first person now pins the weapon to the camera directly, replacing the bone-driven pose outright rather than correcting it, which makes alignment exact by construction and immune to whatever the idle animation is doing underneath it.
  **This now extends to hip-fire too**, not just ADS - which means `MAX_AIM_YAW_FIRST_PERSON`/`spine_pitch_share_first_person`'s *original purpose* (pointing a bone-driven weapon at the camera) no longer applies in first person at all; the weapon's own orientation stopped being derived from the spine the moment the hold took over. Left in place regardless, not reverted, because `_apply_spine_aim()` still runs unconditionally every frame and the spine bones it twists are still parents of the grip-arm bones `_solve_grip_arm_ik()` solves from - the torso correction now only matters indirectly, through where it leaves the *shoulder* for that IK to reach from, not through the weapon's direction directly. Confirmed by probe this doesn't cause a problem in practice (grip-arm accuracy measured sub-centimetre in both hip-fire and ADS with spine-aim left running exactly as-is) - flagged here so a future reader doesn't go looking for a weapon-pointing effect these two values no longer have in first person.
- **The rifle set's sprint is empty-handed.** Mixamo's sprint clips swing both arms, so the weapon swings with the hand rather than being carried — measured, they hold the hands only `+0.03m` to `+0.13m` above the hips against `+0.24m` to `+0.31m` for the jog tier. That's why `_apply_spine_aim()` releases the torso above `sprint_blend > 0.5` instead of trying to correct it. The pistol set has no such problem, because it has no sprint clips at all and reuses its run.
  Investigated as a reported bug ("rifle sat in hand during sprint") before being traced back to this same gap: the rifle pack does have real 8-way `sprint_*` clips (not a normal-tier fallback — `LocomotionSets.has_distinct_sprint(&"rifle")` is true), and `_solve_support_arm_ik()`/`_align_world_model()` both re-run every `_process` frame off the live bone pose, so the weapon does track the hand correctly frame to frame. There's no code bug and no frame-rate/timing dependency found in `attach_world_model`/`_align_world_model`/`process_priority` ordering (`AnimationTree` → `player` → `WeaponController`, all `_process`-based, no physics-interpolation setting in `project.godot` to disagree between machines). The clip itself is just this static-looking by design once the spine-aim release above is added on top — fixing the *look* needs a sprint clip pack that actually carries a rifle (see the Mixamo clip list), not a code change.
- **Bug found by testing: the player could freeze mid-jump, animation-locked until landing (sometimes not even then).** `jump_up` is a one-shot; its clip length has no relationship to how long the actual jump arc takes. If it finished *before* the character reached the peak (still rising, `is_on_floor()` still false), `_on_animation_finished()` cleared `active_full_body_animation` but left `airborne_animation` at its stale `&"jump_up"` value - the only place that cleared it was inside the landing branch, which this wasn't. `_update_animation()`'s airborne branch only re-triggers a clip when `desired_air_animation != airborne_animation`; recomputing `&"jump_up"` again next frame (still rising) matched the stale value and skipped playing anything at all, leaving `animation_tree.active` false with nothing driving the pose for the rest of the arc - recoverable only if landing happened to force a fresh `jump_down` afterward. Fixed by clearing `airborne_animation` unconditionally in `_on_animation_finished()`, not just inside the landing branch, so the airborne check always sees a real mismatch and re-requests whatever's actually appropriate (`jump_loop` by then) the very next frame. Reproduced and confirmed fixed with a probe that fires `_on_animation_finished()` while artificially still-airborne, rather than by eye - the race needs a one-shot short enough to finish before the arc peaks, which depends on jump height/gravity/the clip's own length, so it doesn't reproduce on every jump.
- **The pistol set doesn't visibly crouch.** The pack ships no crouch-walk, so `crouch` reuses the walk tier: the capsule shrinks and the camera drops, but the body stays standing. `kneeling_idle` is a kneel, not a gait, and is only used for the crouch square's centre.
- **A weapon switch re-points an `AnimationNodeAnimation`'s clip immediately, but the model swap itself can now be delayed by a holster clip.** `_on_weapon_changed()` → `_play_draw_animation()` looks up `LocomotionSets.draw_clip_installed_name(set)` and plays it filtered to the upper body (same `AnimationNodeOneShot` pattern as fire/reload) if `anim_player.has_animation()` finds it, and is a silent no-op otherwise - skipped on the player's very first equip at game start (nothing is being drawn "from"), and run on every subsequent switch regardless of whether the two weapons share a locomotion set (swapping AK-47 for M4A1 still re-grips). `assets/animations/rifle/draw.res` and `pistol/draw.res` both exist now; a set with none still swaps with no animation, exactly as before this hook existed.

  **`play_holster_animation(set_name)`** is the other half, called by `WeaponController.equip_slot()` *before* it swaps anything - see that function's own comment in `scripts/weapons/CLAUDE.md`. Plays the outgoing set's holster one-shot (same upper-body-filtered `AnimationNodeOneShot` shape, its own `HolsterAnimation`/`HolsterShot` pair chained above `DrawShot` in the blend tree) and returns the clip's length; `WeaponController` uses that to actually defer the swap rather than doing it instantly. Returns `0.0` - swap immediately, same as before this existed - if the outgoing set has no `"holster"` key or no clip on disk (every set but rifle currently; `assets/animations/rifle/holster.res` is the only one that exists). `LocomotionSets.holster_clip_path()`/`holster_clip_installed_name()` mirror the `draw_clip_*` pair exactly, and `_install_extra_clips()` loads a holster clip the same optional, missing-is-fine way it loads a draw clip.

Manual test scene: `scenes/levels/test_arena.tscn` (flat ground, one hand-placed zombie, `RoundDirector` present but `autostart = false` so it never spawns waves) — open it in Godot and press F6 to run just that scene. Set up for hand-position/grip and (once it exists) ragdoll testing specifically: `test_arena.gd` (attached to the scene root) fills the player's loadout with every weapon in the game at `_ready()` - cycle through with number keys/scroll wheel - and `pause_enabled = false` is set directly on the `Player` node, so Esc there just releases the mouse (the pre-pause-menu behavior) instead of opening the pause menu mid-test. Both are specific to this scene; `town.tscn`'s player is untouched (`pause_enabled` defaults `true`, normal wall-buy-gated loadout).
